BIR Summary List of Sales and Purchases .DAT generator for VAT-registered businesses

A single-binary tool that turns a sales or purchases CSV into the RELIEF .DAT file you submit as the Summary List of Sales and Purchases. It builds every record from one field table, checks each one against the Bureau's own rules, and refuses to write a file that would be rejected — naming the row and the column at fault. It runs on your own computer and sends nothing anywhere.

VAT-registered SMEs and their bookkeepers Philippines · BIR RR 16-2005 s.4.114-3 · RMC 24-2002 · BIR RELIEF

What it does

A VAT-registered taxpayer has to submit, with each quarterly return, a Summary List of Sales and a Summary List of Purchases: one line per customer and per supplier, for each month, in the Bureau's own electronic format. The format is a flat comma-separated file with the extension .DAT, produced by the Bureau's RELIEF data entry module — and the whole difficulty of the job is that the file either matches that format exactly or it is rejected.

This tool does that one thing properly. Give it a CSV of the month's rows and it:

  • reads the CSV defensively — byte-order mark, any line ending, headings in the usual spellings, title rows above them, blank and short rows, thousands separators, a peso marker;
  • adds together the rows that name the same taxpayer, because a summary list carries one line per customer or supplier for the month, and writes the records in alphabetical order by name as the regulation requires;
  • builds the header record and the detail records from a single field table, checking as it goes that the writer and the table still agree;
  • validates every field — width, required, characters, number format, date format, the totals — and refuses to write the file at all if anything would be rejected, listing each offending row and column;
  • names the file the way the validation module expects, because that module reads your TIN, the list and the period back out of the name and checks them against the contents;
  • writes both the plain file and the copy carrying the submission validation key, in the single-byte encoding the format uses.

Who it's for

VAT-registered small and medium businesses in the Philippines, and the bookkeepers and accountants who do their monthly and quarterly BIR work. If you have more than a handful of customers or suppliers, hand-building the .DAT is slow and rejection-prone; a spreadsheet cannot produce it at all, because the format is not a CSV export — the quoting rules differ between the header and the detail records, nil is written one way in one and another way in the other, and the header has to carry totals that match the records exactly.

The rule it implements

Under section 4.114-3 of Revenue Regulations No. 16-2005, a VAT-registered person must submit, together with the quarterly return, a summary list of sales and a summary list of purchases, giving for each buyer and each seller their name, TIN, address, and the exempt, zero-rated and taxable amounts with the tax. The regulation requires the list to be alphabetically arranged and to consolidate the month's transactions per customer or supplier.

The same section says the list must conform to the electronic format prescribed in a Revenue Memorandum Circular, and offers three ways to produce it: the Bureau's own Data Entry Module, an Excel template, or the taxpayer's own extract program. A taxpayer who takes the third route must run the result through the Bureau's validation module. That is exactly what this tool is: an extract program. It does not replace the validation module, and you should still run the file through it before submitting.

The record format itself was prescribed by Revenue Memorandum Circular No. 24-2002 as technical annexes. Those annexes are not published in a form we could obtain, so the layout implemented here was taken instead from the Bureau's own reference implementation: the routine in the RELIEF data entry module that writes the file, cross-checked field by field against the routine in the matching validation module that accepts or rejects it. Where the two agree, which is nearly everywhere, that is as close to ground truth as exists outside the Bureau.

The record layout

The file is a comma-separated flat file, not fixed-width. Each record ends with a carriage return and a line feed. It is a single-byte file in the Windows code page the Bureau's module was built on, not UTF-8. A file holds one header record, first, followed by its detail records — and nothing else. There is no trailer or control record: the header carries the totals, and there is no record count anywhere in the file.

Two quoting rules apply, and they are not the same:

  • In the header, a text field is always enclosed in double quotes, empty or not — so an unused name field is written "".
  • In a detail record, a text field is enclosed only when it has a value. An empty one is written as nothing at all, so two separators sit side by side: ,, rather than ,"",.

Amounts are the same way round:

  • In the header, every total carries two decimal places, including nil: 0.00.
  • In a detail record, a figure carries two decimal places but nil is written as the single digit 0.

There is no escape mechanism of any kind. A comma inside a value would split the record, and the validation module refuses one outright; a quote inside a value would end the field early, and the module that writes the file strips it. So values are cleaned before they are written, and anything that cannot be cleaned is refused.

Summary List of Sales

Header record, 17 fields:

 1  H                      the record type
 2  S                      the transaction code
 3  TIN of owner           quoted, exactly 9 digits
 4  owner registered name  quoted, 50
 5  owner last name        quoted, 30
 6  owner first name       quoted, 30
 7  owner middle name      quoted, 30
 8  owner trade name       quoted, 50
 9  owner address line 1   quoted, 92   (unit, street, barangay)
10  owner address line 2   quoted, 74   (district, city, postal code)
11  total exempt sales     bare, 2 decimal places always
12  total zero-rated sales bare
13  total taxable sales    bare
14  total output tax       bare
15  RDO code               bare, exactly 3 characters: district 44 is 044
16  tax month              bare, MM/DD/YYYY, the LAST DAY of the month
17  month the accounting year ends, 1 to 12, or empty

At least one of fields 4 to 8 must have a value, and at least one of 9 and 10.

Detail record, 15 fields, one per customer per month:

 1  D                      the record type
 2  S                      the transaction code
 3  customer TIN           quoted when present, 9 digits; may be empty
 4  registered name        quoted, 50
 5  last name              quoted, 30
 6  first name             quoted, 30
 7  middle name            quoted, 30
 8  address line 1         quoted, 30
 9  address line 2         quoted, 30
10  exempt sales           bare, 2 decimal places, or 0 when nil
11  zero-rated sales       bare
12  taxable sales          bare, net of the tax
13  output tax             bare
14  TIN of owner           bare (not quoted), the filer's own 9 digits
15  tax month              bare, the same date as the header's

At least one of fields 4 to 7 must have a value. A company fills 4 and leaves 5, 6 and 7 empty; an individual does the opposite. The customer's TIN may be left empty, for a sale to someone who is not registered.

Summary List of Purchases

The header has 21 fields: the same first 10, then the six totals (exempt, zero-rated, services, capital goods, other goods, input tax), then the creditable and non-creditable input tax, then the RDO code, the tax month and the month the accounting year ends. The validation module insists that the total input tax equals the creditable and non-creditable amounts added together.

The detail record has 17 fields: the same first 9, then exempt purchases, zero-rated purchases, taxable purchases of services, of capital goods and of goods other than capital goods, the input tax, the filer's TIN and the tax month. Unlike a sales record, a purchases record must give the supplier's TIN and an address.

The file name

The name is not decoration. The validation module reads it apart by position and checks it against the contents, and offers to rename a file that does not fit:

<9-digit TIN><S or P><MM><YYYY>.DAT

004123456S102026.DAT   sales for October 2026
004123456P102026.DAT   purchases for the same month

One file per month, not per quarter: a VAT quarter is three sales files and three purchases files.

The TIN, and why there is no branch code

Every TIN field in this format holds exactly nine digits — no dashes, and no branch code anywhere: not in the header, not in a detail record, not in the file name. The branch code belongs to other BIR formats, and advice to include one here is advice about a different file. If your CSV carries one it is read, reported, and left out. A TIN that is a run of a single digit is refused, because the validation module refuses it.

The characters a value may contain

The validation module checks every text field against a fixed list. Besides the control characters, it refuses " $ & ' , \ ` | and everything above the plain ASCII range — with one deliberate exception, Ñ, which it allows because Filipino surnames need it.

Two of those are common in real business names, so this tool substitutes them and tells you it did: an ampersand becomes the word AND, so SMITH & SONS stays recognisable, and an apostrophe is removed. Accented letters other than Ñ are folded to their plain form, text is upper-cased as the Bureau's own entry screens upper-case it, and every change is reported against the row it came from. Nothing is altered silently.

The submission copy

The Bureau's validation module writes a second copy of a validated file into a folder of its own, with one extra line at the end: a twenty-character validation key derived from the file's name, the number of records, their total length and a checksum of their contents. It then tells the user that that is the copy to attach for electronic submission.

This tool produces both. The plain file is what you give the validation module; the copy in the eRelief folder is the one with the key. The key algorithm is reproduced exactly from the module that generates it — but whether the current submission channel still requires that line is something we could not confirm, so both files are to hand and you can use whichever yours asks for.

Install & run

It is one Go program with no dependencies beyond the standard library, so there is nothing to install and nothing to configure.

git clone https://github.com/sreenivas-sadhu-prabhakara/bir-slsp-dat-generator-csv.git
cd bir-slsp-dat-generator-csv

# build a single binary
go build -o bir-slsp-dat-generator-csv .
./bir-slsp-dat-generator-csv

# or just run it
go run .

Then open http://127.0.0.1:8080/ in a browser. Two flags change the defaults:

./bir-slsp-dat-generator-csv -addr 127.0.0.1:9000 -data ~/bir/slsp-data.json

It also runs once from the command line, which is what a month-end script wants. It exits 0 when the file was written, 1 when it was refused, and 2 when the arguments or the CSV could not be used at all:

./bir-slsp-dat-generator-csv \
    -csv sales-october.csv -list sales -period 10/2026 \
    -tin 004-123-456-000 -name "ABC Trading Corporation" \
    -address "123 Main St Brgy San Antonio|Makati City 1203" \
    -rdo 044 -out ./filings/

# print the whole record layout and stop
./bir-slsp-dat-generator-csv -layout

# write a CSV template to start from
./bir-slsp-dat-generator-csv -sample purchases > purchases-template.csv

What it stores

One JSON file on your own computer, ./bir-slsp-dat-generator-csv-data.json by default, holding the filing taxpayer's details so you do not retype them each month, and the last 25 files you built so you can download one again. It is written atomically — to a temporary file that is then renamed — so an interrupted write cannot corrupt it, and it is created readable only by you.

Nothing else leaves the machine. The tool binds to 127.0.0.1, makes no outbound network calls of any kind, has no accounts, no analytics and no telemetry, and loads no fonts, scripts or styles from anywhere but itself. Your customers' and suppliers' names, TINs and figures never go anywhere. Delete that one file and the tool knows nothing.

Features

The layout lives in one place

Every field, width, token and quoting rule is one table. The writer names each field as it fills it and stops if the table disagrees, so the code and the format cannot drift apart.

It refuses rather than guesses

Nothing is written if any record would be rejected. You get a list of CSV rows and columns to fix, each named by line number, instead of a file that looks finished.

Byte-exact output

Both quoting conventions, both ways of writing nil, CR LF line endings, and a single-byte encoding in which Ñ is one byte and not two.

Defensive about your CSV

Byte-order mark, any line ending, four separators, headings in many spellings, title rows, blank rows, short rows, thousands separators, a peso marker. Bad cells are reported by line, never guessed.

Consolidated and alphabetical

Rows naming the same taxpayer are added together and the records are sorted by name, which is what the regulation asks for and what the Bureau's module does.

Totals that always agree

Amounts are whole centavos, so the header's totals are exactly the sum of the records — the one cross-check the validation module performs on the file as a whole.

Nothing changed in silence

Every substitution — an ampersand, an apostrophe, a shortened address, a dropped branch code — is reported against the row it came from.

Both copies, and the layout

The plain file for the validation module and the keyed copy for electronic submission. -layout prints the whole field table so you can check it yourself.

Assumptions & settings
  • Value-added tax at 12% — the rate imposed under the National Internal Revenue Code as amended. It is a single named constant, used only to check that a tax column is consistent with its taxable column, never to work the tax out. A figure more than ₱1.00 away from the rate is remarked on, never refused, because a party may be partly zero-rated or exempt. It can be overridden for a period when another rate applied. Confirm the current rate with the Bureau.
  • Header totals must match the detail records. The validation module allows a difference of up to ₱2.00; this tool makes them agree exactly, because it computes them from the records it writes.
  • Amounts are held in whole centavos, so a thousand records total exactly with no drift.
  • Negative amounts are refused by default: the list has no column for one, so net returns, discounts and credit memos against the month's figures. A setting lets one through if you have been told to file it that way.
  • One month per file. The tax month is the last day of the month and appears on every record, with leap years handled by the calendar rather than a table.
  • A branch code is never written, because the format has no field for one.
  • Field widths are the Bureau's module's own column widths: 50 characters for a registered name or trade name, 30 for each part of an individual's name and for each of a customer's or supplier's two address lines, 92 and 74 for the filer's two, 3 for the RDO code. A longer value is shortened and you are told.
  • Ceilings the validation module imposes: at most 25 fields per record and 254 characters per field, because it reads the file into a table of that shape; and at most 600 characters per record, because the routine that appends the submission key reads no further and drops the rest without a word. A record that long is refused.
What could not be sourced, and what it means for you
  • The layout itself is sourced from the Bureau's RELIEF data entry module and its matching validation module, field by field, from the code that writes the file and the code that accepts or rejects it. Both agree. -layout prints every field with how well it could be sourced.
  • The prescribing annexes to RMC 24-2002 could not be obtained in a published form. The layout here comes from the Bureau's reference implementation instead — arguably the stronger source, since the validation module is what actually accepts or rejects your file, but it is not the text of the circular.
  • Whether the module we read is the current one could not be confirmed. It is the latest version we could obtain, and no later one is referred to anywhere, but the Bureau's download pages have since moved. Check the version offered on the Bureau's own site before relying on this for a filing.
  • No real, published .DAT file could be found to compare against, byte for byte. The output was derived from the writing routine and checked against the validating routine, not against a specimen.
  • Whether electronic submission still requires the validation key line could not be confirmed. The algorithm is certain; its current necessity is not. Both copies are produced, so you can use whichever your submission channel asks for.
  • Line endings are a carriage return and a line feed, which follows from the file-writing call the module uses, rather than from a published specification.
  • The regulation asks for more than the format carries. RR 16-2005 lists “sales subject to final VAT withheld” and the purchases equivalent as required content, but the RELIEF record layout has no field for them. This tool follows the layout, because that is what the validation module checks.
This tool builds a file from figures you give it. It does not check them against your books, your returns or your invoices, it does not decide what is taxable, exempt or zero-rated, and it is not tax, accounting or legal advice. Run the file through the Bureau of Internal Revenue's own validation module before you submit it, and confirm the current format, the deadlines and the submission channel with the Bureau or a qualified practitioner.
